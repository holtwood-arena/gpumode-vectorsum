# 2026-11-08 调研结论与 kernel v2

## 调研（4 个 subagent，并行三路 + 交叉批判）

结论已写入 `NOTES.md`。本次推翻了 11-07 的三条判断：

| 先前判断 | 核实结果 |
| --- | --- |
| 必须全程 float64 累加 | 错。官方 correct 解是 fp32 `data.sum()`；危险的是跨块 fp32 顺序累加，不是块内 fp32 树 |
| B200 FP64 被砍到 1.2 TFLOPS | 错。那是 B300/GB300；B200 是 CC 10.0，FP32:FP64=2:1，FP64≈37 TFLOPS |
| 需要 CUDA Graph 压 launch 开销 | 错。`clear_l2_cache` 的 268 MB fill 在计时前跑，掩盖了 launch 开销 |

新掌握的关键事实：
- **计分只取最后一个 benchmark case**（size=52,428,800）。
- 现役榜：B200 37.033 / H100 67.922 / A100 101.237 / L4 692.015 μs。
- 选卡：A100 最优（119 人但头部稀，85% 带宽即 rank 3），L4 次之（45 人，断档）。
- 模板首行榜名错误：官方写 `vectorsum_py`，现役榜是 `vectorsum_v2`，不一致会直接报错。

## 代码变更

`kernels/vectorsum_v2/submission.py` v1 → v2：

1. 块内累加器从 `tl.float64` 改为 **fp32**（树形归约后转 fp64 存部分和），
   跨块仍是 fp64。依据：块内 fp32 树 + 跨块 fp64 最坏情形余量 ≥62x，而全 fp64
   在 L4 上会吃掉 36~67% 的访存地板。
2. `_BLOCK` 1024 → **4096**，`ITERS` 8，`num_warps` 4 → **8**：per-program 元素数
   8192 → 32768，52.4M 的 program 数 6400 → **1600**。
3. 新增 `EVEN` constexpr：所有 benchmark size 都是 `_PER_PROG=32768` 的整数倍，
   走无 mask 快路径；测试尺寸（1023/1024/1025/2048/4096）走 mask 路径。
4. 加载加 `eviction_policy="evict_first"`（流式读，不污染 L2）。
